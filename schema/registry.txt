# Bedlam — stable identity registry
#
# The ONLY hand-maintained input to the manifest generator, and deliberately small.
# See docs/SCHEMA_AND_EVOLUTION.md §2.
#
# IDs are ALLOCATED here, never derived. An ID derived from source order,
# declaration order, layout order, or a compiler symbol hash works perfectly until
# the first refactor, at which point every save, replay, recorded input log,
# connected older client, and in-flight rolling deploy reinterprets the same bytes
# as different fields. Silently.
#
# Rules, all enforced at build time by src/schema/manifest.zig:
#
#   - A new identity takes the next unused ID in its space.
#   - Removal tombstones the ID. Tombstoned IDs are NEVER reusable. There is no
#     override flag and none will be added; the temptation arrives about once a
#     year and the cost of yielding is unbounded.
#   - Renaming preserves the ID. A rename is a declaration change, not an
#     identity change.
#   - Changing a field's wire type requires a NEW id, the old one tombstoned, and
#     a migration edge.
#   - ID spaces are separate per kind.
#
# FORMAT
#
#   component <Name>              id=<hex>  introduced=<ver> [deprecated=<ver>]
#   component <Name>.<field>      id=<hex>  introduced=<ver> [deprecated=<ver>] wire=<type>
#   event     <Name>              id=<hex>  introduced=<ver>
#   rpc       <Name>              id=<hex>  introduced=<ver>
#   lease     <Name>              id=<hex>  introduced=<ver>
#   tombstone <kind> <Name>       id=<hex>  retired=<ver>
#
# A dotted name denotes a field, whose ID is <component>_<index> — the component
# ID in the high half, the field index in the low half.
#
# `wire=` on a field pins its encoding. docs/SCHEMA_AND_EVOLUTION.md §10 check 3
# requires detecting a wire-type change made without a new ID; pinning it here
# catches that at build time rather than requiring a diff against the previously
# released manifest. Extension to §2's format, for that reason.
